# DSH 迁移到 Zig + quickjs-ng 完整组件方案

> 版本：v1（基于 deepseek-harness 仓库 @0.1.1-rc.2 源码调研，2025-08 实测）
> 目标：把 DeepSeek Harness 从"Node.js 单进程承载一切"迁移为"Zig 宿主 + quickjs-ng 引擎 + 多 context 生命周期"，使 8~10 个并发项目 + 数十个 subagent 的资源占用从"无上限线性爆炸"变为"一个进程内一组廉价、互不干扰的 context"。

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| core 能不能用 Zig 写 | **不能也不该**。cordis 内核（vendor/cordis）**0 个 `node:` import**，是纯 JS；插件是 JS 模块，cordis 的对象就是插件对象 |
| 真正的 Node 强耦合 | 只有两处：① loader 的 import seam（穿透 Node 内部 `internal/modules/esm/loader`，~200 行 + NAPI addon）；② 一组 Node 专有 API（sqlite / stripTypeScriptTypes / async_hooks / vm / worker_threads / node-pty / koffi / sharp） |
| 资源恐怖的根源 | ① 每个 dsh 进程 V8 基线 ~205MB（实测）；② subagent 全部 in-process，N 个项目 × M 个子代理的会话状态全挤在**同一个堆**；③ 换掉引擎即除根，无泄漏由编码纪律保证（§6.2） |
| 迁移的正确姿势 | **cordis 契约不动，宿主世界全部换成 Zig**：一核（Zig event loop）一栈（quickjs-ng）多 context（会话/子代理生命周期即 context 生命周期） |
| 预期收益 | 单进程基线 205MB → 40~70MB；10 项目 + 数十 subagent 收敛为**一个 host 进程内的数十个廉价 context**；code-runtime 每次执行 50~80MB → 10~20MB；单二进制分发。占用由架构决定，无泄漏由编码纪律保证 |
| 最大风险 | 开放插件生态的 ESM/CJS 加载语义（bun 级工程）；AsyncLocalStorage 语义；Windows（ConPTY/ACL） |

## 1. 调研依据（证据链）

### 1.1 实测基线（本机，dsh web 运行中）

```
27737  node dsh web        Rss: 205 MB   ← 宿主进程
27367  npm exec dsh web    Rss: 152 MB   ← npm 包装（与上者部分共享）
27736  sh -c 'dsh' web     Rss: 1.8 MB
```

本机 16G 内存，Minecraft JVM 占用 ~8.3GB，free 仅 641MB，swap 已用 759MB。205MB 基线在 10 进程场景下 = 2GB+。

### 1.2 cordis 内核无 Node 依赖（关键事实）

```
vendor/cordis/src   — 0 个 node: import（context/fiber/registry/events/service/index/logger/reflect/utils）
vendor/cosmokit/src — 0 个 node: import
vendor/cordis dependencies: @standard-schema/spec + @deepseek-ai/cosmokit（皆纯 JS）
```

### 1.3 Node 耦合分布（全仓库逐包扫描，~230 个包）

- **纯 JS、零 Node import 的包 ≈ 85%**（全部工具层、UI、会话逻辑、goal/jobs/compaction、客户端——它们只依赖 cordis/cosmokit/zod/schemastery，可在 quickjs-ng 直接跑）。
- **深度 Node 耦合包（12 个，是重写焦点）**：

| 包 | Node 依赖 | 性质 |
|---|---|---|
| subprocess-local | child_process, stream, node-pty, koffi | 进程/PTY 后端 |
| fs-local | fs, buffer, koffi | 文件系统后端 |
| sandbox-local / sandbox-windows-acl | child_process, koffi, node-addon-landlock-run | 沙箱后端 |
| session-persistence-sqlite / session-query-sqlite / storage-sqlite | **node:sqlite** | SQLite 后端 |
| session-persistence-jsonl | fs, zlib, koffi, perf_hooks | JSONL 后端 |
| attachment-local | fs, crypto, **sharp** | 图片处理 |
| code-runtime-worker-thread | worker_threads, node:module(stripTypeScriptTypes) | 代码执行后端 |
| workflow-worker-thread | worker_threads, node:vm | 工作流后端 |
| cordis-host-runner | node:vm | 动态插件宿主半部沙箱 |
| agent | node:async_hooks (AsyncLocalStorage ×2) | 上下文传播 |
| host-directory-picker-native | child_process, koffi | win32 对话框 |

- 其余包对 Node 的使用是**碎片化单点**：`node:path`(394) / `node:fs`(202+246) / `node:os`(238) / `node:url`(197) / `node:crypto`(64) / `node:child_process`(55) / `node:http`(43) / `node:stream`(29) —— 全部可由 shim 层覆盖。

### 1.4 插件模型与启动链

```
dsh bin (apps/cli) → runProfile → app-boot (profile/bundles/patch 组合)
   → cordis-plugin-loader: EntryTree → 每行 cordis.yml → Entry.init()
   → tree.import() 三分支：
       1) 'cordis:' 前缀 → loader.builtins 直取
       2) loader.internal → Node 内部 ESM ModuleLoader.import(name, baseUrl, attrs)
          （经 node-addon-require-builtin 穿透 --expose-internals 边界；Node22=v1 / Node24=v2 双形状）
       3) 无 internal → '.' 相对路径走 import(new URL)；裸包名走 import(name)
   → unwrapExports(ESM/CJS default 归一化) → ctx.plugin(fiber) → 生命周期
```

- 默认 web profile 插件行：base patch **78 行** + web-app patch **84 行**（含 patch 覆盖语义，实际启动 import 数十个模块）。
- 插件来源开放：用户 `dsh plugin <pkg>`(转发 pnpm)、profile `cordis.yml`、`cordis.patch.yml`、agent preset、SDK/ACP 等——**依赖闭包不可预知**。
- `vendor/`（cordis/cosmokit/loader/group/include/hmr/timer/logger-console）全部在仓库内，可改。

### 1.5 会话/子代理状态模型（内存 vs 磁盘）

| 子系统 | 现状 | 内存驻留 |
|---|---|---|
| 会话事件 | `session-persistence-sqlite`：事件全量落 sqlite（DatabaseSync），按需 loadStored | 磁盘为主；live session + projection 在内存 |
| 大工具输出 | `spill` 家族：超限输出落 session 目录文件，只留预览 + locator | 磁盘为主 |
| 会话历史窗口 | `compaction-basic` / `compaction-*` / `token-meter` | 有压缩机制 |
| **subagent** | **全部 in-process**（fork-in-process / spawn-in-process / in-process-driver），registry 支持 `ready`（仅存储、可恢复）状态 | **所有活跃子代理会话的完整上下文在同一个堆** ← 恐怖主因 |
| workspace | `workspaceRegistry` 已在：单实例多工作区、每工作区 session 账本、持久化顺序 | 原生设计意图就是单实例 |

### 1.6 LLM / 代码执行契约（对迁移友好的好消息）

- `ctx.llm.stream()` 返回 **`AsyncIterable<StreamChunk>`**（不是 ReadableStream）→ Zig fetch 只需暴露 async iterator，**不需要完整 WHATWG Streams**。
- `llm-deepseek` 用全局 `fetch` + `eventsource-parser`（消费 `response.body` 的 reader）→ 需实现 fetch + SSE，但事件源解析是纯 JS。
- code-runtime 契约：`run(program, bindings, signal)`，bindings 是 lossless-JSON async 回调；执行 = `stripTypeScriptTypes` + `new AsyncFunction` 于独立 worker 线程。**quickjs-ng 后端天然更优**（独立 context + `JS_SetInterruptHandler` + `JS_SetMemoryLimit`）。

## 2. 目标架构

```
┌─────────────────────────────────────────────────────────────────┐
│ dsh（Zig 单二进制, ~5-15MB 原生, 静态链接, @embedFile 打包 app JS）  │
│                                                                   │
│  Zig 宿主核心                                                      │
│  ├─ 事件循环: epoll/kqueue/io_uring + timer heap + signal + job 队 │
│  ├─ Module Editor: quickjs-ng ESM linker + npm 解析 + CJS 包装     │
│  ├─ Context 管理器: 创建/销毁生命周期（会话即 context，关闭即释放）  │
│  ├─ 服务层 (Zig 实现): fs·subprocess·sqlite·http·ws·fetch·pty·      │
│  │    crypto·watch·timer·spawn·env                                  │
│  └─ 桥接: JS 侧薄 facade (host.bindings) + cordis HostModuleLoader  │
│                                                                   │
│  quickjs-ng 运行期                                                  │
│  ├─ system context   cordis + 全部插件 + 服务门面 (常驻, 预算 64-96MB)│
│  ├─ session ctx ×N   每项目/会话一个, 预算 32-64MB, LRU 热窗口 2-3   │
│  ├─ subagent ctx ×M  每子代理独立, 数 MB 量级, 完成/关闭即释放        │
│  ├─ code ctx         模型生成代码, 预算 8-16MB + interrupt 超时      │
│  └─ workflow ctx     脚本执行, 预算 16-32MB                          │
│                                                                   │
│  外部: bash/pwsh/python/dsh-sdk 子进程 · sqlite 文件 · spill 文件    │
│        浏览器 UI (apps/web Vite 产物, 静态 + WS, 零改动)              │
└─────────────────────────────────────────────────────────────────┘
```

**核心原则**：cordis 内核一行不改；官方插件树可 99% 原样（纯 JS 包占大头）；所有"Node 专属能力"替换为 Zig 服务实现 + quickjs 引擎原语；**所有状态从"堆里活着的对象"迁移到"磁盘上的事实"**。

## 3. 组件分类矩阵

| 组 | 定义 | 处理 | 占比 |
|---|---|---|---|
| **A 重写层** | 运行时基础设施：module loader、event loop、服务实现、引擎 shim | 全部 Zig 新写 | 约 12 包对应 |
| **B 直接可跑** | 零 Node import 的纯 JS 包 | 原样打包进 quickjs run | ~85% 包 |

| **F 弃用/替换** | node-addon-require-builtin、koffi、node-pty、sharp、chokidar、undici、ws | Zig/系统库替代 | 6 项 |

## 4. 组件级处理明细

### 4.1 启动链（cli → profile → loader）

| 组件 | 现状 | 方案 |
|---|---|---|
| apps/cli bin | 动态 import 分派（profile/plugin/dump-config） | Zig 二进制内置相同分派；`--profile` 语义不变 |
| profile-boot | app-boot 组合 bundles + patch 层 | 原样（纯 JS，B 组）；由 system context 执行 |
| 插件发现 | 读 `dsh.profile.bundles` / `cordis.patch.yml`（js-yaml + `!!js` 表达式） | 原样；`!!js` 表达式在 quickjs eval 域内求值（需提供 `process` 等全局） |
| `dsh plugin` | spawnSync pnpm | Zig spawn 同语义（A） |
| process-shutdown | process 信号 | Zig signal 处理 + `exit` 事件（A） |

### 4.2 module loader（**全方案最难，bun 级工程**）

quickjs-ng 原生只有"从回调读源码"的模块加载器。需要实现：

1. **解析**：node_modules 向上遍历、`package.json` `exports`/`imports` 条件（`import`/`node`/`default`、subpath、self-reference）、目录 `index.js`、scoped 包；`require()` 语义（CJS 兄弟）。
2. **CJS 包装**：`(module, exports, require, __dirname, __filename)` 包壳 + `require` 走同一解析；exports 互操作：`default` + `__esModule` 判别（官方包已是 ESM/bundled，第三方 CJS 插件需要）。
3. **格式**：ESM（快照编译）、CJS、JSON（`with {type:'json'}` import attributes 需要）、WASM（可选，M5）。
4. **语义**：module 缓存 + 循环引用（CJS 先放 `exports` 后执行）、`import.meta.url`、动态 `import()`、`top-level await`（quickjs-ng 支持性需验证，见 §9）、`import.meta.resolve`（可选）。
5. **builtins 注册表**：`node:*` 与裸 `fs` 等映射到 `@dsh/shims/node-*` JS 层 + Zig binding 两层结构。
6. **`cordis:` 直取路径**：保留 loader.builtins 捷径。

**与 cordis 的对接（vendor 内修改，最小 diff）**：

```ts
// vendor/loader/src/host-loader.ts（新）
export interface HostModuleLoader {
  import(specifier: string, baseUrl: string, attrs: ImportAttributes): Promise<any>
}
// vendor/loader/src/config/tree.ts（改）
- if (this.ctx.loader.internal) return await this.ctx.loader.internal.import(...)
+ if (this.ctx.loader.host) return await this.ctx.loader.host.import(name, baseUrl, {})
```
- Node 适配器：保留原 `internal.import`（Node 版继续全量兼容）；
- Zig 适配器：调用 guest 侧 `host.import`（quickjs module loader 驱动）；
- `vendor/loader/src/internal.ts` 的 `node-addon-require-builtin` reach-in 只保留给 Node 适配器；Zig 版不再需要。

### 4.3 cordis 内核

**不动。** 唯一侵入是 §4.2 的 loader seam 与 `Loader.internal` 字段语义（`host` 新字段）。fiber/registry/inject/events/isolate 全部原样。

### 4.4 会话与持久层

| 组件 | 现状 | Zig 方案 |
|---|---|---|
| session-persistence-sqlite | `node:sqlite` DatabaseSync（prepare/get/all/run/exec/close + 命名/位置参数、事务） | **实现 `node:sqlite` shim**：Zig 绑定 sqlite3（同进程链接 `libsqlite3` 或 vendored amalgamation），镜像 DatabaseSync 小 API。API 面小（~15 方法），难点低 |
| session-persistence-jsonl | fs + zlib + koffi(win32 MoveFileExW) | fs + zlib(Zig) + win32 API 直调 |
| storage-json / storage-sqlite / storage-domain | 通用 KV 域 | sqlite shim + fs（A） |
| session-query-sqlite | 同上 + 只读查询 | sqlite shim（A） |
| spill-local | fs | fs（A） |
| workspace / session-projection / session-reference | 纯逻辑 | B 组原样 |

**context 生命周期**（新增，非替换）：会话/子代理 == 一个 quickjs context；关闭即 `JS_FreeContext`（+`JS_FreeRuntime`），模块图/字符串表随之整体释放。应用层状态大小归 session-persistence/compaction/spill 管（已存在），运行时只管"存在即小、关闭即清"。

### 4.5 子代理（资源问题的第一现场）

**现状问题**：in-process 子代理的完整语境（消息/工具结果/投影）与宿主同堆，N 子代理 = 堆线性膨胀。

**分层修复**：
1. **短期（Node 上先做）**：subagent registry 对"已完成"子代理只保留 `latest report` + sqlite 日志指针，`ready` 状态从"驻留对象"改为"磁盘记录"（registry 已有 ready 语义，落地释放引用即可）—— 不需要 Zig。
2. **中期（Zig context 模型）**：每个 `fork/spawn` 子代理 = 独立 quickjs context（数 MB 量级，含完整 cordis 子 fiber 图）；生命周期 = 子代理生命周期，结束即释放；恢复 = 从会话日志回放（session-persistence 已有一切）。
3. **进程型 provider（acp/claude-code/codex/dsh-sdk）不变**——它们本来就是外部进程，Zig spawn。

### 4.6 工具层

全部 B 组（工具 = 纯 JS，契约 `ctx.tools` + schema + 展示层），**唯一特例**是底层执行器：
- `tool-bash` / `terminal-bash` / `bash-local` / `bash-sandbox` / pwsh 系：**契约不变**，执行经 `ctx.subprocess`（A 组 Zig 实现）。
- `tool-fs` / `tool-fs-search` / `str-replace-editor`：经 `ctx.fs`（A 组）。
- `tool-web` / web-search-*：经 `globalThis.fetch`（A 组 Zig fetch）。
- `tool-workflow`：经 workflow-worker（§4.10/4.11）。
- `tool-cordis`：动态插件（§4.2 + §4.12）。

### 4.7 LLM 层

| 组件 | 现状 | 方案 |
|---|---|---|
| llm（契约） | `AsyncIterable<StreamChunk>` 瀑布 | 原样（B） |
| llm-deepseek | 全局 fetch + eventsource-parser（SSE） | Zig fetch（HTTP/1.1+TLS+代理+重定向），返回带 `body.getReader()` / `[Symbol.asyncIterator]` 的最小 Response 对象；eventsource-parser 原样跑（B） |
| llm-pi-ai | fetch + os/fs/path | 同上 |
| llm-retry / llm-replay / llm-mock-server | 纯逻辑 / node:http 测试服务 | retry/replay 原样；mock-server 由 Zig http 承载（测试用） |
| token-meter | 纯 JS | 原样 |

**fetch 实现范围**（够用集）：请求方法/头/正文（字符串、Uint8Array、JSON）、`AbortSignal`（自己实现）、响应流（分块传输 + chunked decode）、gzip(可选)、TLS（Zig std.crypto.tls 或外接）、代理（环境变量 `HTTPS_PROXY`，M4）。LLM 只需它 + SSE；浏览器行内事件、FormData 不需要。

### 4.8 沙箱/权限

| 组件 | 现状 | 方案 |
|---|---|---|
| sandbox-local | child_process + landlock-run（C11 原生 launcher，已存在！） | **Zig 直调 landlock-run 二进制**（它是独立的 `landlock-run <cmd>` CLI，Rust/Zig 侧只是定位它 + grantArgs）——或者未来用 `@cImport` 内联规则集（Linux） |
| fs-sandbox / fs-observation-policy | 在 ctx.fs 层做 fencing | **Zig fs 层做策略**（写检查在 native 侧，比 JS 包装更可靠） |
| sandbox-windows-acl | koffi FFI 调 win32 令牌/ACL | Zig `std.os.windows` 直接调（M5） |
| 权限模式 / user-approval / permission-presets | 纯 JS | 原样 |

**迁移红利**：agent 工具层运行时在 system context，Zig 宿主可在其子进程 spawn 时强制 landlock/seccomp，无需 JS 配合。

### 4.9 代码执行（code-runtime）

- 契约：`run(program, bindings, signal) → CodeRunResult`，`CodeBindingFunction` 是 lossless-JSON async 回调。
- **新后端 `code-runtime-quickjs`**：独立 context + `JS_SetMemoryLimit`(8-16MB) + `JS_SetInterruptHandler`(超时) + 绑定注入（全局对象 = bindings，null-prototype）；程序体经 erasable-only TS 剥离（自实现 ~300 行：注释/类型注解剥离，够 `stripTypeScriptTypes` 同等子集；`enum`/命名空间等非可擦除语法 → 报错，与现状一致）。
- 消息：async 回调经 `ctx.call`（Zig ↔ quickjs 桥）直接执行——**不需要跨线程序列化**，比 worker 快一个量级。
- Python 后端（code-runtime-python）不变：外部子进程。

### 4.10 工作流（workflow-worker-thread）

- 现状：worker_threads + `node:vm`（SourceTextModule 级沙箱）+ JSON-RPC 往返。
- 方案：quickjs context（专用 runtime），引擎级 sandbox；worker 语义替换为 context；`agent()`/`pipeline()`/schema 校验契约不动（纯 JS 引擎栈 consumer）。
- 收益：无跨线程序列化、无 50-80MB worker、超时/内存硬控。

### 4.11 动态 Cordis 插件（cordis-host-runner / tool-cordis / client-runner）

- `cordis-host-runner` host 半部现在用 `node:vm`（createContext + runInContext）评估模型提交的代码。
- 方案：quickjs 新 context 评估（**更安全**：`JS_SetMemoryLimit` + interrupt + 无 process 逃逸面）；注册表/授权流/fiber 生命周期原样。
- 浏览器半部（client-runner）+ `run` 往返协议：**零改动**。

### 4.12 宿主网络层（web 面）

| 组件 | 现状 | 方案 |
|---|---|---|
| host-webserver | `node:http` createServer + 自有路由 | Zig HTTP server（HTTP/1.1 + keep-alive；mime/静态文件由 frontend-static 逻辑移到 Zig 或 JS facade） |
| client-connection | `ws` WebSocketServer（下链） | Zig WS server（RFC6455，无扩展；mask/分帧/心跳），API 面 = 现有 downlink 调用 |
| frontend-static | node:http + fs | Zig 静态服务 + 304/range |
| api-gateway / api-remotes / apiproxy | HTTP + fflate(gzip) | Zig 路由 + gzip（fflate 可留 JS 侧，纯 JS） |
| directory-picker-* | browse（HTTP）/native（koffi win32 对话框） | browse 原样；native 用 Zig win32 API（M5） |

### 4.13 存储/设置/凭据/技能/预设

| 组件 | 现状 | 方案 |
|---|---|---|
| settings-file / credentials-local / skill-filesystem | chokidar + yaml 热加载 | 保留 yaml（JS）；**文件监听** → Zig `watch`（inotify/kqueue/ReadDirectoryChanges）暴露 `fs.watch` 子集 API |
| agent-presets / persona / skill | 纯 JS 发现/装载 | 原样 |
| home-paths / anonymous-user-id / atomic-write | fs/os/path | shim + Zig fs |
| launch-environment / shell-env / native-command | env/子进程 | Zig spawn + env 快照 |

## 6. 内存模型：架构决定占用，编码决定不泄漏

> 结论先行：**不做前置的预算/快照/换出系统**。Zig 小、quickjs-ng 小、每 context 廉价——"8-10 项目 + subagent 很恐怖"的病根是 V8（一个堆 + 每 worker 50-80MB isolate），换掉引擎后病根即除。剩余工作只有一条：**别泄漏**。

### 6.1 为什么架构本身就够了

| 项 | Node/V8 | Zig + quickjs-ng |
|---|---|---|
| 每 dsh 进程基线 | ~205MB（含 V8、npm 包装、libuv 线程池） | 40~70MB |
| 每会话/每 subagent | 与主进程共享**同一个堆**，互相推高 GC 压力 | **独立 context**，数 MB 量级；创建/销毁都是廉价原语 |
| 每 worker（code-runtime/workflow） | 完整 V8 isolate 50-80MB | 不需要：独立 context（§4.9/4.10） |
| 多项目的正确姿势 | 只能多进程（每进程 205MB 起） | **一个 host 进程内多 context**——进程数 = 1 |

所以：多个项目 + 多个 subagent 同时活跃在架构上就是"一个进程 + 一组小 context"，不存在需要"限制"的量。

**唯一保留的硬限制是安全边界，不是资源管理**：不受信代码（code-runtime 的模型生成程序、workflow 脚本、动态插件 host 半部）使用 `JS_SetMemoryLimit` + `JS_SetInterruptHandler`——这是防止跑飞/死循环，与"内存优化"无关。

### 6.2 不泄漏清单（Zig 宿主编码纪律）

quickjs-ng 的内存模型：值引用计数（`JSValue` 必须显式 `JS_FreeValue`）+ 对象 mark-sweep（不主动还 OS，需 `JS_RunGC`）+ **context/runtime 生命周期手动**。泄漏几乎都发生在边界处：

1. **JSValue 有唯一 owner**：包装成带析构的 guard（Zig `defer` 即可），禁止裸 `JSValue` 跨 await/跨函数逃逸。
2. **桥接调用帧**：每次 host↔guest 往返结束后释放全部临时值；guest 侧 pending promise 的持有值必须由 callback 持有并在 resolve 时释放。
3. **context/runtime 生命周期 = 会话生命周期**：会话/子代理关闭即 `JS_FreeContext`（+ 若 per-session runtime 则 `JS_FreeRuntime`），模块图/字符串表/原子表随之整体释放——**结构性杜绝跨会话泄漏**。
4. **模块缓存归属 runtime**：module cache 挂 runtime 而非宿主全局结构，防止 context 关闭后模块仍被 pin 住。
5. **timer/signal/job 队列**：context 销毁前清空挂起 job，取消全部注册的 host 回调（JS 侧已有 cordis effect disposer；Zig 侧 watch/timer 必须随 fiber/disposer 释放）。
6. **interrupt handler 复位**：每次代码执行后复位 `JS_SetInterruptHandler`，防止残留中断标志破坏后续执行。
7. **异常路径**：每次 `JS_Eval`/`JS_Call` 后检查 exception，`JS_GetException` 与 `JS_FreeValue` 严格配对。
8. **空闲期 `JS_RunGC`**：mark-sweep 不主动归还 OS，长驻进程 idle 时跑一次 GC 防 RSS 棘轮——这是卫生习惯，不是预算管理。
9. **值守手段**：测试注入 Valgrind/ASAN；运行期只留"存活 context 数 + 每 context 内存戳"的诊断计数（仅供归因，不做任何限制）。
10. 若某 context 长期占用大——先查泄漏；排掉泄漏后仍大，那是**应用层状态问题**（会话真的很大），由既有 session-persistence/compaction/spill 负责，不归运行时管。

### 6.3 预期数字（架构自然达成，非限制达成）

| 场景 | 现在（Node） | 目标（Zig + quickjs-ng） |
|---|---|---|
| 空载基线（1 进程） | ~205MB | 40-70MB |
| 10 个项目（每项目一进程） | 10 × 205MB = 2GB+ | **1 进程** + 10 context |
| 追加 N 个活跃 subagent | 同一个堆，线性互推 | 每 context 数 MB；互不干扰 |
| code-runtime 单次执行 | worker 线程 50-80MB | context 10-20MB（为安全边界，非预算） |
| 会话关闭后 | 对象仍在堆里等 GC | context 整个释放，即关即清 |
| 崩溃影响 | 一个 OOM 全没 | 单 context 失败，其余存活（隔离是架构带来的） |
| 启动时间 | 数百模块 import | 预编译 bundle + 二进制内嵌，目标 <300ms |

> 快照换出/LRU/预算机：**从方案中移除**；如果未来实测（M4 后）表明需要（例如单会话真的巨大到想换出），再按 §6.2 第 10 条的归因结果引入为按需功能。

## 10. 关键决策记录

1. **不重写 cordis**；唯一侵入是 loader seam 的 `HostModuleLoader` 接口（M0）。
2. **不动 WebUI（已定）**：apps/web + packages/client/ui 全部零改动；宿主侧 HTTP/WS 运输协议**冻结为规范**；Vite 构建产物原样打包进 Zig 二进制并由 frontend-static 语义服务；现有 vitest.web 快照套件原样作为兼容性门禁。
3. **无缝兼容（分层定义，详见 §8.1）**：二进制层/数据层/契约层/生态层四层红线；"任意 npm 包都能跑"明确不承诺，代之以"cordis 插件契约 + 文档化 Node API 子集 + 能力检测 + 明确报错"。
2. **顺序倒置保护**：M0/M1 在 Node 上完成，全部收益产生于 Zig 之前；Zig 从 M2 起可随时回退。
3. **资源策略**：不做前置预算/换出系统；占用由架构（引擎 + context 模型）决定，不泄漏由 §6.2 编码纪律保证；唯一保留的硬限制是**不受信代码安全边界**（code-runtime/workflow/动态插件的 `JS_SetMemoryLimit` + interrupt），与资源优化无关。
4. **LLM/工具/会话契约（AsyncIterable、bindings、persistence backend、spill、loader Entry）是迁移的"宪法"**——任何一侧都不允许跨越这些契约搞特殊。
